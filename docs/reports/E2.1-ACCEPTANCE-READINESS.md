# E2.1 — Cierre de aceptación de RC1

Fecha: 2026-10-21. Candidata para aprobación: [SPEC-E2.1-CANDIDATE.md](../specs/SPEC-E2.1-CANDIDATE.md).

## Veredicto

**GO para revisión/aprobación documental; producción pendiente de autorización.** Se concretan los siete bloqueos del NO-GO anterior en reglas y fixtures reproducibles. Ningún resultado de esta matriz es una prueba ejecutada.

Existe una incompatibilidad material entre las propuestas 1 y 5: al responder un Echo Request dirigido a otra IP del router, la IP origen del Reply debe ser la IP solicitada, aunque salga por otra interfaz. La candidata propone explícitamente C1: IP de salida para errores ICMP; IP destino del Request para Echo Reply; TTL inicial 64 y MAC de salida en ambos. Requiere aprobación. [RFC 1812 §4.3.3.6](https://www.rfc-editor.org/rfc/rfc1812.html#section-4.3.3.6), [RFC 1122 §3.2.2.6](https://www.rfc-editor.org/rfc/rfc1122.html#section-3.2.2.6).

Se solicita aprobar también las precisiones C2–C5 de §1.2: épocas internas invalidan timers pero no identifican paquetes viejos idénticos; fallo de egreso previo a la primera emisión cierra la sesión; ARP de 3 s e ICMP de 2 s conservan sus tiempos; las reconfiguraciones de direcciones/rutas se limitan al tráfico detenido. Son decisiones de cierre visibles, sin implementación silenciosa.

| D6 / 6 | Interfaces /31 solo en enlace directo PointToPoint, dos direcciones utilizables y sin broadcast dirigido. | [RFC 3021 §2.1–2.2](https://www.rfc-editor.org/rfc/rfc3021.html#section-2.1); CIDR-03/04. Una ruta CIDR /31 no exige crear un enlace. |

Los valores TTL 64/timeout de 2 s, el rechazo estricto de claves de ruta y la restricción de configuración son políticas de PacketLens; no se atribuyen a RFC como valores obligatorios. `session_epoch` no se añade al payload ICMP.

## Convenciones de ejecución

Todas las pruebas son **propuestas, aún no escritas ni ejecutadas**. La columna ID se corresponde exactamente con un requisito de la candidata. Cada fila aporta Arrange/Act/Assert; puede dividirse en micropruebas del mismo ID.

Rust: `cidr_routes`, `acceptance`, `lifecycle`, `harness`, `regression` son módulos propuestos. Los casos que necesitan hooks privados viven dentro del crate; no se hace pública una sonda para alojarlos en tests externos. C#: el nombre completo es `Clase.Método`, con clase indicada por tabla; puede usar internal visible al ensamblado de tests. Cada implementación mantiene helpers y protocolos independientes.

F1–F8 remiten a las fixtures exhaustivas de §8 de la candidata. I = TEST-01, A = TEST-02. Variantes usan motor nuevo salvo continuación explícita. Para contar eventos, la traza debe ser suficiente o recogerse incrementalmente sin pérdida; no se asume cardinalidad global a partir de una ventana truncada.

## Arquitectura y pendientes reales

Se cierran los límites: valores CIDR/rutas, estado host/router, scheduler E1 y observación de dominio; arnés privado de entradas. Rust/C# siguen independientes. No hay motor común, ECS ni capas UI nuevas. El servicio Echo del router reutiliza la decisión de salida de dominio, pero no se convierte en un comando ping originado por usuario.

Pendiente: aprobar RC1, incluida excepción C1 y precisiones C2–C5. No queda pendiente inventar fixtures ni diseñar presentation/v2 para comenzar S1. C2 es una limitación explícita de correlación ICMP; no se añade un nonce o protocolo para ocultarla.

Tras aprobación: baseline E1 ejecutada, primer RED funcional mínimo S1, GREEN, REFACTOR. Nano limita código al caso; milli añade variaciones CIDR/prefijos que impiden sobreajuste; primary revisa dominio/scheduler/adaptadores. Compilación e infraestructura se registran aparte y no acreditan comportamiento. Se conservarán goldens E1 y la comparación cruzada.
