# E2.1 — Incremento 03: intercambio real entre subredes

Fecha de cierre: 2026-10-23. Fuente normativa: RC1 aprobada de `SPEC-E2.1-CANDIDATE.md`, incluidas C1–C5; E1, addendum, ADR-0001–0004 y `TDD-POLICY.md` permanecen protegidos.

## Resultado y alcance

Implementado el camino exitoso completo **E2.1-S1**, independientemente en Rust y C#: host1 → sw1 → r1 → sw2 → host2 y respuesta. No es una implementación completa de E2.1 ni una réplica binaria de Packet Tracer.

- Host configurado E2 decide destino on-link o gateway para ARP, conservando el destino IPv4 original. El receptor decide su propia ruta de vuelta; responder no crea una sesión ping.
- Router admite ARP dirigido a la IP de entrada, aprende/responde en esa interfaz y no conmuta ni propaga ARP a otra subred.
- Caché, cola y resolución ARP del router se aíslan por interfaz y next hop. Una resolución agrupa varios paquetes FIFO. Se conserva el contexto original de recepción para la futura supresión ICMP; no se reconstruye causalidad.
- Reenvío con LPM sobre rutas y operatividad reales, IP origen/destino conservadas, TTL decrementado una vez y cabecera Ethernet semántica nueva. Desencolar o reintentar ARP no vuelve a decrementar TTL ni a enrutar el paquete.
- Renovación por ARP válido, no por uso/IPv4; expiraciones y retries obsoletos reconocen épocas. Se reutilizan constantes, transmisión diferida y validaciones de enlace E1.
- Servicio Echo local del router: comprobar IP propia antes de TTL de tránsito; Request con TTL 0/1/64 puede responder. Reply nuevo TTL 64, id/seq conservados, IP origen igual a la IP solicitada (C1), MAC de salida. No se crea sesión ping del router.

Se corrigieron dos defectos C# expuestos por regresiones: cerrar la sesión con el destino remoto original, no con la IP del gateway cuya resolución falló; y no dejar una sesión oculta al rechazar un comando remoto todavía no soportado por falta de gateway.

### Límites explícitos

**No se dan por implementados S2–S8, ICMP 3/0, 3/1 o 11/0, timeout de sesión, TTL configurable, correlación de errores ni `presentation/v2`.** No se tocó el frontend.

Las ramas de TTL de tránsito agotado, ausencia de ruta del router, entradas IPv4 no admitidas y agotamiento final ARP del router terminan por ahora con diagnóstico `RouterIcmpErrorPathPending`. Evita un reenvío/respuesta silenciosamente incorrecto, pero **no equivale al descarte/ICMP normativo**, no completa esas pruebas de aceptación y debe retirarse al implementar cada rama. Tras ese diagnóstico no se garantiza continuar la simulación: desechar esa instancia. En particular, el descarte FIFO final y Host Unreachable del router están pendientes.

Un comando remoto de host sin gateway sigue rechazándose antes de crear sesión; la prueba protege atomicidad, **no acredita HOST-01/S3**, que requerirán el descarte y terminal normativos. La vuelta fallida de Echo en el receptor tampoco queda aceptada como S7. No se cambia RC1 para justificar estas limitaciones del incremento.

## Complejidad relevante (análisis, no benchmark)

Sea D número de dispositivos, I interfaces del router, R rutas, L enlaces, N vecinos por interfaz y M datagramas retenidos, Q tamaño de heap. Identificadores y PDU E1 tienen tamaño acotado en este modelo.

- Comprobaciones de IP propia/broadcast: O(I), sin asignar tablas nuevas en Rust. LPM conserva las implementaciones del incremento 01: Rust recorre R rutas y consulta operatividad mediante mapas, O(R·(log D + log I + log L)); C# reconstruye su vista de rutas, ordenando conectadas, O(I log I + R) y espacio transitorio O(R), con búsquedas de diccionario esperadas O(1). No se introdujo trie ni se afirma una aceleración.
- Caché/resolución Rust: O(log D + log I + log N) por consulta; C#: O(1) esperado por clave compuesta, no garantía de peor caso constante. Encolar al final cuesta O(1) amortizado, además de localizar la cola y emitir su observación.
- Desencolar M paquetes: O(M) recorridos y M inserciones DES O(log Q) cada una, más consultas de extremo. No repite LPM ni decremento TTL. Timers de renovación/retry también se insertan O(log Q).
- Estado ARP/pendientes: O(vecinos + resoluciones + M), más las PDU/contextos originales retenidos, eventos pendientes y traza acotada por capacidad. Renovar deja timers obsoletos hasta procesarlos; no se implementa compactación del heap. La cola de paquetes por resolución no tiene un límite nuevo en este incremento.
- Se conserva `has_active_work()` indexado Rust; los timers de router se incorporan a su clasificación, no se restaura un recorrido del heap por iteración. C# conserva su clasificación/recorrido previo. El comparador, guardas, constantes y resultados E1 no cambian.

Riesgos pendientes: crecimiento de colas/timers bajo cargas grandes, coste de reconstruir vistas de rutas C# y finalización de ramas negativas/sesiones. No se optimizan sin cargas y benchmarks reproducibles.
