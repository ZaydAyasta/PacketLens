# E2.1 — Incremento 01: CIDR, configuración IPv4 y rutas

Fecha: 2026-10-21. Fuente normativa: `docs/specs/SPEC-E2.1-CANDIDATE.md` RC1, aprobada expresamente por el responsable del proyecto, incluidas C1–C5. Metodología: `docs/engineering/TDD-POLICY.md`.

Resultado: implementado el primer incremento en Rust y C#, con modelos independientes. No se declara implementado E2.1-S1 ni el conjunto completo de requisitos CFG/RT que depende del futuro procesamiento de tráfico.

## Alcance y protección del árbol

Antes de editar se inspeccionó Git. Ya existían modificaciones en `AGENTS.md`, la eliminación de `TDD-POLICY-DRAFT.md` y archivos sin seguimiento para la política definitiva, RC1 y la matriz de aceptación. Se conservaron; no se hizo reset, checkout, stash, staging ni commit.

Se tomó un inventario SHA-256 de los archivos existentes, incluidos los no seguidos, antes de modificar producción. La comprobación posterior detectó cambios únicamente en cuatro archivos previamente existentes: `lib.rs`, `SimulationEngine.cs`, `SimulationErrors.cs` y el `Program.cs` del evaluador. Los documentos previos, especificaciones, goldens, tests E1 existentes, frontend, exportadores y contratos `presentation/v1` conservaron su contenido. El índice no tiene cambios de esta tarea.

Implementado:

- Longitud de prefijo encapsulada, máscaras `/0..32`, normalización en orden de red, pertenencia y broadcast dirigido.
- Valores inmutables de dirección/prefijo de interfaz y gateway opcional, con validación de dirección utilizable, subred e IP propia.
- Adaptador de configuración de host que conserva la API E1; los hosts que optan por la nueva configuración tienen una sola interfaz IPv4 seleccionada. Configuración sin emitir eventos ni avanzar el reloj.
- Guardia `EngineBusy` para esa configuración, incluida la entrada antigua de configuración de interfaces cuando el host ya usa configuración E2.1. Revalidación atómica del gateway al cambiar dirección/prefijo.
- Modelo inicial de router con al menos dos interfaces; conectadas derivadas y reservadas, estáticas, errores tipados, rechazo de duplicados normalizados y reconfiguración atómica que revalida las rutas existentes.
- LPM entre rutas operativas: especificidad, no métrica ni inserción; recuperación de rutas sin borrar su configuración.

No implementado: dispositivo router dentro del scheduler, envío remoto por gateway, reenvío, nuevos ICMP, TTL configurable, sesión/timeout E2.1, validación topológica `PointToPoint`, contratos v2 ni interfaz gráfica. Los valores `/31` tienen ambos extremos utilizables, pero **no** se declara aceptado tráfico `/31` ni cumplido CIDR-04. El gateway queda configurado; todavía no cambia la decisión de envío E1.

## Paridad y determinismo

`Compare-E21Configuration.ps1` ejecuta un ejemplo Rust y un modo del evaluador C# que construyen entradas equivalentes de forma independiente. No comparte código de dominio ni traduce la implementación de un lenguaje al otro. Sus representaciones difieren: Rust conserva un vector de rutas derivadas más estáticas y un `BTreeMap`; C# conserva un diccionario de interfaces y una lista de estáticas, proyectando las conectadas al consultar.

Cada ejecutable reconstruye su proyección 100 veces y exige igualdad local. El script compara después las líneas de ambos motores exactamente: 33 observaciones CIDR, 8 de gateway, 24 de LPM (6 destinos × 4 estados operativos) y 4 de motivos de next hop, total **69**. Se ejecutó con resultado `SemanticallyEqual=True`, `IndependentRunsPerEngine=100`. Es una sonda de pruebas, no un contrato público nuevo ni un golden.

## Complejidad y límites arquitectónicos

Análisis teórico, **no medición de rendimiento**. Sea `I` el número de interfaces, `S` el de estáticas, `R=I+S`; se consideran IDs de tamaño acotado y un predicado operativo de coste constante.

| Operación | Rust | C# |
| --- | --- | --- |
| Máscara, normalización, pertenencia y gateway | Tiempo/espacio auxiliar O(1) | Tiempo/espacio auxiliar O(1) |
| Construcción de conectadas | O(I log I), almacenamiento O(I) | O(I) esperado con diccionario/hash, almacenamiento O(I) |
| Añadir estática validada | O(R), espacio amortizado O(1) además de la entrada | O(R), espacio amortizado O(1) además de la entrada |
| LPM | O(R), espacio auxiliar O(1), devuelve referencia | O(I log I + R), espacio auxiliar O(R): proyecta/ordena conectadas antes de recorrer |
| Reconfiguración atómica | Cota O(I log I + S·R), staging O(R) | Cota O(I + S·R) esperada, staging O(R) |
| Guardia de host sin tráfico | Consulta al índice activo O(1) y mapa de pings vacío | Escaneo de pendientes O(Q), con Q = cola; el scheduler C# previo no se optimiza aquí |

Las diferencias de coste interno no afectan la semántica probada. No se añade trie, índice de rutas ni optimización de scheduler sin mediciones. La proyección C# por consulta es una limitación explícita a perfilar si crece la carga.

Los módulos IPv4/rutas no dependen de presentación ni de la simulación. El adaptador de host es pequeño y opt-in para preservar construcciones E1. No hay ECS, plugins ni jerarquías anticipadas. Al adjuntar el futuro router al motor, el dueño de la simulación deberá suministrar estado operativo real y aplicar la misma exclusión de configuración durante tráfico; un callback de prueba no demuestra ese cableado.
